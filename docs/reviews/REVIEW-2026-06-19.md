# Review 2026-06-19

Status: Packet 04 contract/security review filled.

Scope: current public-safe MemoryCore MVP scaffold.

## Verification Baseline

```bash
python3 -m memorycore.cli eval --public-safe
python3 scripts/validate_mvp_contract_security.py
```

## Correctness

Findings:

- No high-severity correctness issue found in the public-safe contract surface.
- Medium: `schemas/result.schema.json` lagged current LCM normalized output:
  LCM result pointers include `summary_id` and `conversation_id`, and LCM `get`
  results include `citations`. Packet 04 updates the result schema so these
  fields are documented response data rather than undocumented drift.
- Request validation behavior is now covered by
  `MEMORYCORE_CONTRACT_SECURITY` for valid `search`/`get`/`verify` requests,
  missing-query rejection, and unsupported-operation rejection.
- Error routing for unsupported verification keeps `verification_state` on the
  nested structured error, which is schema-valid and sufficient for callers to
  avoid freshness overclaiming.

## Readability

Findings:

- No high-severity readability issue found.
- Contract/security docs now name stable request/result/error invariants,
  response-only retrieved data fields, persistence-safe fields, and forbidden
  fields directly enough for validation scripts to check them.
- The dedicated contract-security eval keeps its checks grouped by contract,
  persistence, retrieved-content handling, and observability.

## Architecture

Findings:

- No high-severity architecture issue found.
- Packet 04 keeps MemoryCore positioned as a control plane: result responses may
  include immediate `snippet`, `content`, and `citations`, while audit,
  provenance, and observability remain pointer-first and content-sparse.
- No live adapter behavior, MCP behavior, or OpenClaw smoke artifacts were
  changed.

## Security

Findings:

- No critical issue found in the public-safe fixture path.
- Medium: before Packet 04, the retrieved-content-as-data rule was present in
  the threat model but not enforced by a dedicated validation target. The new
  eval checks that contract/threat docs explicitly distinguish retrieved
  content from instructions.
- Medium: audit/provenance leak checks existed in separate evals but were not
  tied to the packet's named end eval. `MEMORYCORE_CONTRACT_SECURITY` now
  validates generated audit and provenance records against the forbidden
  private-content field list.
- Observability now has an explicit allowed operational field set and default
  forbidden field set, including raw snippets, content, citations, summaries,
  answers, transcript/source/prompt text, credentials, tokens, account ids,
  local private paths, and raw backend exception fields.

## Performance

Findings:

- No performance issue found in Packet 04 scope.
- The contract-security eval uses only static fixtures, in-process
  normalization, schema validation, and generated temporary records. It does
  not call live backends or write persistent audit/provenance files.
